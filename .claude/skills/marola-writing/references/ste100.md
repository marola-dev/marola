# STE100 in marola: what the plugin skill does not say

The rules of ASD-STE100 Simplified Technical English are in the Writing Skills plugin's
`asd-ste100` skill and its `references/REFERENCE.md` (surendranb/writing-skills@2e692b8, pinned in
`.claude/settings.json`). Load that skill first. This file adds only the marola parts: the items
that do not change, the rules that marola sets, the procedure, and the report.

Adapted from h0ffmann/picasso@2d6f8d8, `.claude/commands/ste100.md` (the steps and the list of
items that do not change) and `docs/whitepapers/determinism-2026/STE100.md` (the two passes and
the report). The lesson on normative words is from ouroboric-dev/ouroboric@b355b1d,
`docs/6-journal/2026-10-11-the-style-guide-applied-to-itself.md`. Licences: the root `REUSE.toml`.

Neither the plugin nor this file contains the ASD dictionary of approved words. If `asd-ste100`
does not load, say so in the report. Do not write the rules from memory.

## 1. What does not change

Change only the prose. Do not change these items:

- code blocks, inline code, commands, file paths, URLs and link targets;
- headings, because other files link to their anchors;
- table structure, and YAML front matter;
- names of products, repos, models, labels, flags, tests and people;
- numbers and their units, dates, commit hashes, `§n` and `R<n>` identifiers;
- quotations, citation markers and reference lists.

In a MIP, also keep these items:

- The metadata table and the *Readiness* table keep their rows and their row names.
- The **Status** value keeps the vocabulary of `.claude/rules/docs.md`.
- The **Blocked by** value stays as it is. `scripts/mip_graph.py` reads it.
- The section numbers and titles of `docs/MIPs/TEMPLATE.md` stay as they are.

## 2. Which source wins

Use the first source that has a rule for the case:

1. `AGENTS.md` and the template of the document.
2. This file.
3. The plugin's `asd-ste100` skill and its `REFERENCE.md`.

Marola sets these rules. Each one differs from the plugin skill or adds to it:

| Subject | Marola rule | Reason |
|---|---|---|
| Future tense | Permitted. Use it for each thing that is not built. | A `Draft` or `Accepted` MIP describes a design. The present tense says that the design exists. The plugin skill says to avoid the future tense. |
| Simple past | Permitted for a check or a result that has a date. | "Checked 2026-10-13" is a fact about the past. |
| -ing forms | Do not use one as a verb or as a noun, in body text also. | Picasso's command sets this. The plugin skill limits it to titles. Technical names keep the form ("routing"). |
| Headings | Do not change a heading, even one with an -ing form. | Other files link to the anchor. |
| Vocabulary | The plugin wins. "Test" is a noun: "do the test". | Picasso's command permits "test" as a verb. The plugin's reference does not. |
| Semicolon, contractions | Do not use them. | The plugin's reference sets this. Picasso's command has no rule. |
| Technical names | Repo, module, tool and test names are approved terms. | The standard permits project terms. |

## 3. Procedure

1. Load `asd-ste100`. Read its `REFERENCE.md` for the limits and the word rules.
2. Read the full text. List each group of terms that the text uses for one thing.
3. Select one term for each group. Use the term that the code or the other docs use.
4. Rewrite one sentence at a time.
5. Do not remove a fact, a condition, a number, a limit or a reference.
6. If a sentence cannot obey a rule, keep the fact and make the words simpler.
7. Keep a citation or a link at the end of the group of sentences that it supports.
8. Run the counter on each file:
   `python3 .claude/skills/marola-writing/scripts/ste_check.py <file>`.
   Add `--tables` to count the table cells also.
9. Correct each finding, or record it for the report with its reason.
10. Do the check pass of §4.
11. Write the style marker of `SKILL.md` §1 in a document that is not STE100 by default.
12. Write the report of §5.

The counter measures sentence length and paragraph length only. It counts each word in
parentheses, which is more strict than the plugin's reference. A text with no finding can still
break the word rules. Marola has no automated check for those rules.

For a long document, divide the rewrite by section between agents. Then one agent does the check
pass on the full text, because two agents can select different terms.

## 4. Check pass

Read the new text against the original, sentence by sentence. A second agent that did not do the
rewrite gives a better check.

- Find each meaning that the rewrite made weaker, made stronger or lost. Restore it from the
  original.
- Compare the normative words. "Should" does not become "must". "Can" does not become "will".
  A change of force is a design decision, and only the owner makes it.
- Make sure that one term has one meaning in all sections.
- Search for -ing forms, phrasal verbs, contractions and semicolons.
- Make sure that each link, anchor, identifier and number of §1 is the same as before.
  `git diff --word-diff` shows a changed number or identifier quickly.

## 5. Report

Give these items to the person who asked for the rewrite:

1. the files that changed, with the counter's totals before and after;
2. each sentence that stays outside the rules, with the reason (a quotation, a citation, a name);
3. each requirement or decision whose meaning or force possibly changed, for the owner to confirm;
4. each error in the original that the rewrite found and did not correct;
5. the checks that did not run, such as the vocabulary check when `asd-ste100` did not load.

## 6. Limits

- Do not rewrite a scientific paper to STE100 unless the owner names the file.
- STE100 is an English standard. Do not apply it to Portuguese text.
- After an STE100 rewrite, do not run a humanizer skill on the text.
