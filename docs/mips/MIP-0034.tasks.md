Decisions taken so the tasks above are unambiguous (all from MIP-0034 §4.1's 2026-09-08 revision):

1. **Geometry, not names.** Matching is point-in-polygon against each alert's CAP `<polygon>`.
   `AlertAreas.byArea`, the hand-written mesoregion→`areas.json` table in the first draft, is
   **not built**. This is what makes the path work for all of Brazil: a new area in `areas.json`
   needs no new mapping row.
2. **Two severity vocabularies, both kept.** Order by CAP's `Moderate`/`Severe`/`Extreme`; display
   INMET's `Perigo Potencial`/`Perigo`/`Grande Perigo` verbatim. Never translate INMET's words.
3. **RSS is the index, CAP is the content.** The `<description>` HTML table is a fallback for
   fields CAP lacks, not the parse path.
4. **`/avisos/ativos` JSON is not used in these tasks.** It is richer (GeoJSON, IBGE codes,
   `aviso_cor`) but undocumented; adopting it is a later, separate change that must degrade to
   RSS+CAP when it moves.
5. **No scoring change.** MIP-0034 §6 and the 2026-09-08 re-probe reached this separately:
   `Swimability.score` is untouched, and an alert suppresses nothing. Whether `Grande Perigo` /
   `Extreme` should suppress a recommendation is a human decision and needs its own MIP.
6. **No LLM on this path**, per §5.2. The alert text is INMET's, shown verbatim with its source.

rewriting it (1 adds `core/alerts/`, 2 adds one file in it, 3 touches `Report`, 4 touches `Board`
