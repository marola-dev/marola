**Three independent lanes, not one chain**: the table's numbering is delivery order within a lane,
not a single dependency chain across all seven. Real code dependency:

- **Ledger lane** (1 → 2 → 3 → 4): each based on the previous, per `scripts/stack.sh`'s normal
  numbered-branch convention.
- **Tracing lane** (5 → 6): touches `Telemetry`/`AppConfig`/`cli/Main`, never `RunLedger`; task 5
  branches from `main` directly (not from task 4), task 6 from task 5.
- **DSPy lane** (7): pure Python, zero Scala dependency; branches from `main` directly.

The three lanes can be built in parallel (three fresh sessions/agents at once, per the skill's "one
task, one session" step). Expect one small, mechanical conflict where lanes overlap in
`AppConfig.scala` (ledger adds `MAROLA_MLFLOW_TRACKING_URI`/`MAROLA_MLFLOW_EXPERIMENT`, tracing adds
`MAROLA_TRACES`); whichever lane merges second resolves it on `restack`, not a redesign.

Decisions taken for v1 (MIP §11), so the tasks above are unambiguous:

1. **Local server only, via compose, not nixpkgs** (OQ2): `ghcr.io/mlflow/mlflow` in a
   `docker-compose.yml` profile, never added to `flake.nix`'s default shell or the runtime
   `Dockerfile` (MIP §8: "a heavy Python dependency"). Task 3 pins the exact tag it first uses.
2. **REST over `Http`/`Json`, not the Java client** (MIP §4.2's own pick, restated): task 2's
   `MlflowRunLedgerSpec` is the fallback trigger: if artifact upload over REST proves awkward
   there, swap to `org.mlflow:mlflow-client` for that one call, not the whole ledger.
3. **Experiment naming** (OQ6): `marola/<kind>` as already used throughout MIP §5:
   `marola/benchmark`, `marola/prompt-compile`, `marola/finetune` (later, unbuilt), `marola/traces`.
4. **Azure ML JVM auth** (OQ1) and **self-hosting MLflow on Azure** (MIP §4.5) are not tasks here —
   Phase 2, blocked on Phase 1 and the cost-confirmation gate regardless of MIP status.
5. **`finetune/train_lora.py` logging** (MIP §5's fourth bullet) is not a task here: that script
   is "written, not run" today (MIP-0008); add its MLflow logging alongside whenever it is actually
   run for the first time, not speculatively.
