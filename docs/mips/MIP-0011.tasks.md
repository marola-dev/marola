were, since later tasks read files earlier ones create (`AGENTS.md`'s trimmed body, the hooks

Decisions taken so the tasks above are unambiguous:

1. **Task 8 ships one skill candidate, not four** (MIP §5 item 8 lists four). The remaining three
   (`fixture-refresh`, `benchmark-compare`, `corpus-doc`, `water-provider`, minus whichever ships
   in task 8) are follow-up tasks/PRs off `main` once this stack merges, not bundled here; each
   needs its own `evals/evals.json` and review, and cramming four into one PR would blow past the
   ~400-line guideline.
2. **Task 11's `gh pr merge`/`gh pr close` deny is project-wide**, not scoped to background runs
   only: there is no daytime workflow in `DEV-FLOW.md` §6 that has Claude itself run `gh pr
   merge` (a human merges, per that doc), so a project-level deny costs nothing during normal
   sessions and closes the gap for unattended ones. If a future workflow needs Claude to merge
   under human instruction, that is a new MIP, not a quiet exception carved into this one.
3. **Order 1→11 matches MIP §5's own bullet order**: the MIP already sequenced these by what
   later tasks read (task 6 trims `AGENTS.md` after tasks 2-5 exist to point rules at; task 8
   disables auto-invocation on `mip-tasks`, which this very tasks.md was produced by, so task 8
   should not land before this file is committed). No task reorders the MIP's own sequence.

Restack notes: task 6 is the only one that touches `AGENTS.md` itself (trimming it); every task
before it only adds new files. Nothing else rewrites a file an earlier task created, so restacks
after each merge should be mechanical (`scripts/stack.sh restack`, no manual conflict resolution
expected).
