Decisions taken so the tasks above are unambiguous:

1. **The MIP's test harness does not exist.** §5 says `scripts/site_check.js` is "the stub-DOM
   harness written for MIP-0008 task 6, checked in", checked 2026-09-06: neither
   `scripts/site_check.js` nor `site/fixtures/` is in the repo, and `just quality-other` has no
   Node step. Task 2 creates it, and it precedes the JavaScript tasks so they have a failing
   assertion to turn green. ci.yml's `quality-other` job enumerates its steps (it does not run
   `just quality-other`) and its `changes` filter has no `site/**` group; task 2 adds both, or
   the harness would never run in CI.
2. **`wind_level` is additive and optional.** `hours/items` has `additionalProperties: false`, so
   emitting the field without the schema change breaks `BoardSpec`'s conformance test, so schema,
   `Board` and the specs are one task by necessity, not convenience. `required` is untouched so an
   already-published board stays valid (MIP §5: "an old board still renders, without the band").
3. **`WindLevel` lives in `model/Models.scala`** beside `JellyfishRisk`/`WhaleSightingLikelihood`
   (`derives CanEqual`, `strictEquality` is on); `windLevel` returns `Option[WindLevel]`: the
   MIP's "plus `None` when the forecast lacks wind" is an `Option`, not a fourth case, so
   `windDelta`'s "no wind data" branch stays distinct from a real band.
4. **Open questions closed as proposed in §11:** OQ1 two thresholds, no "gale" band (map and CLI
   agree); OQ2 the hour's whales value plus "best HH:MM" when it differs; OQ4 one wave glyph in
   v1. OQ3 (the same row as the first line of the Telegram reply) stays with MIP-0002.
5. **Task 4 owns the manual check.** §7's desktop-hover / phone-tap / area-zoom check and its
   screenshots go in the last PR's body, once both the tooltip and the card row exist; earlier
   PRs are judged by the harness alone.

Restack notes: task 2 creates `site/fixtures/board.json` and `scripts/site_check.js`; tasks 3 and
4 *extend* the harness's assertions and edit `app.js`/`style.css` in sequence (4 after 3), so no
task rewrites a file an earlier task created, so restacks after each squash-merge should be
mechanical. Task 1 is the only one touching Scala; tasks 2-4 are JavaScript/CSS/HTML/workflow
only and never trigger `quality-scala` on push.
