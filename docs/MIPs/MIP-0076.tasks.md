(`/marola-devkit:mip-tasks`, `stack`). Branch `mip-0076/<k>-<slug>` in the repo the row lands in;
rows of one repo stack on that repo's previous row, and merge bottom-up with `stack restack` after

## Decisions

Stale claims first: the MIP is accepted, so it stays as written and these rows follow today's code
(checked 2026-10-04 on every repo's `main` and devkit `v0.4.1`).

1. **The API docs are a branch, not a release asset.** §5.1 and §11 name `api-docs.tar.gz` as a
   `wiring.allow` entry. MIP-0074 retired that asset (its tasks 35 and 36): marola-ml has no
   `release.yml`, and marola-app's attaches only `ml-resources-<tag>.tar.gz`. Each repo's
   `api-docs` branch is now pushed by the devkit's reusable `api-docs.yml`, and `site-data` by
   app workflows and the umbrella's `site-data-push.sh`. §5.1's source table has no rule for a
   branch artifact, so row 1 adds one. If `fetch-api-docs.sh`'s `<repo>` template still defeats
   the reader rule, the allow entry names the `api-docs` branch instead of the tarball.
2. **The ml image has a reader.** §5.1 says no workflow or script reads
   `ghcr.io/marola-dev/marola-ml`; marola-app's `docker-compose.yml:54` runs it as
   `ollama-local` in the `local` profile. Compose files are not among §4's reader sources, so
   row 1 adds `docker-compose*.yml` `image:` lines, and the allow entry is then not needed. The
   maintainer's decision to keep the image is unaffected, and the maintainer confirmed dropping
   the allow entry (2026-10-05). REPOS.md's "Nothing yet" for it is
   stale too, and row 5 replaces it.
3. **Cross-repo writes are parsed too (maintainer, 2026-10-05).** MIP-0074 task 27 wrote one
   hand-written table of ten rows inside the markers; §5.1 plans four generated tables, and two
   of today's facts are neither pins nor dispatches: the compiled-prompt PRs (a `gh pr create`
   against marola-app in marola-ml's `compile-prompt.yml`) and the OODS ingest (an app workflow
   pushing to marola-oods, arriving with MIP-0056). Row 1's extractor recognises a workflow step
   that opens a PR in, or pushes to, another marola-dev repo, so both stay inside the generated
   block and nothing is hand-written after it.
4. **`wiring.allow` lives at the umbrella root**: the extractor runs there, and the facts it
   excepts are org-wide. The MIP leaves the location open.
5. **Two devkit releases, one consumer bump.** §5.5 releases after step 1 and after step 2, and
   step 3 bumps each code repo. The code repos bump to row 4's tag, which carries the
   `notify-umbrella` change they need; row 14's `graph` and skill reach them with their next
   routine bump ("every repo gets it with its next devkit bump", §5.2). Only the umbrella takes
   row 14's tag in this MIP (maintainer, 2026-10-05).
6. **Self-tests, not pytest.** §7 says "pytest with fixture repos"; the devkit has no pytest on
   its `PATH`, and every tool there is tested as `<tool> --self-test` from `tests/self-tests.sh`.
   Rows 1, 2 and 12 keep §7's case names under that convention.
7. **The umbrella's CI needs more than §5.4 says.** Its `quality-other` job checks out without
   submodules and takes its tools from `nix develop .#lint`, and `pointer-sync.yml` has no Nix
   at all. Rows 11 and 15 add both.
8. **The gap is still there, at newer refs.** On 2026-10-04 every code repo's
   `notify-umbrella.yml` keeps `paths: [README.md, "docs/**"]` and no `event-type`, at `@v0.4.1`
   (app, corpus, ml), `@v0.3.1` (site) and `@v0.3.0` (oods), not the Appendix's `@v0.2.4`.
   graphify is still 0.9.66 at the devkit's locked nixpkgs (`b4fd65b`). The "one-line change in
   five repos" of the Effort row is a full devkit bump in each, two of them across v0.4.x.

Ordering: the extractor goes first because a run over the real workspace (row 1's last test) is
what can still change the block's shape. Row 15 waits on all five consumer rows and a pointer-sync
merge because `wiring --check` reads the pinned commits: it passes only once every pinned caller
really sends `submodule-updated`.
