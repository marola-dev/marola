    MIP-0034 tasks — the INMET alert arm¶

    Ordered delivery of MIP-0034 §5.1/§5.2 only, the inbound operational-alert path, as stacked PRs (.claude/skills/mip-tasks/SKILL.md, scripts/stack.sh). Branch mip-0034/<k>-<slug>, each based on the previous; merge bottom-up, scripts/stack.sh restack after each squash-merge.

    MIP-0034 is explicitly "three separable things, deliberately not one pipeline". The other two, §5.3/§5.4 the reading queue, §5.6 the outbound Atom feed, ship alone, touch none of the files below, and get their own task list when someone wants them. Nothing here blocks them.

    Decisions taken so the tasks above are unambiguous (all from MIP-0034 §4.1's 2026-09-08 revision):

    1. Geometry, not names. Matching is point-in-polygon against each alert's CAP <polygon>. AlertAreas.byArea, the hand-written mesoregion→areas.json table in the first draft, is not built. This is what makes the path work for all of Brazil: a new area in areas.json needs no new mapping row.
    2. Two severity vocabularies, both kept. Order by CAP's Moderate/Severe/Extreme; display INMET's Perigo Potencial/Perigo/Grande Perigo verbatim. Never translate INMET's words.
    3. RSS is the index, CAP is the content. The <description> HTML table is a fallback for fields CAP lacks, not the parse path.
    4. /avisos/ativos JSON is not used in these tasks. It is richer (GeoJSON, IBGE codes, aviso_cor) but undocumented; adopting it is a later, separate change that must degrade to RSS+CAP when it moves.
    5. No scoring change. MIP-0034 §6 and the 2026-09-08 re-probe reached this separately: Swimability.score is untouched, and an alert suppresses nothing. Whether Grande Perigo / Extreme should suppress a recommendation is a human decision and needs its own MIP.
    6. No LLM on this path, per §5.2. The alert text is INMET's, shown verbatim with its source.

    Restack notes: tasks 1→5 form a single line, each adding to what the previous created and never rewriting it (1 adds core/alerts/, 2 adds one file in it, 3 touches Report, 4 touches Board + the schema, 5 touches site/static/ + site_check.js). Task 6 depends only on task 1's parser and touches scripts/ alone, so it can be developed in parallel and merged in any order relative to 3–5, but scripts/stack.sh wants a line, so it is stacked after 5 unless someone splits it out deliberately. Task 7 is docs-only and must merge last, since it flips the MIP's status.

    Open before task 5: the map control's exact shape is the one thing here not pinned by the MIP: "a list/hover like the ranked beaches" is the requirement, and MIP-0046's icon set is the constraint. Worth a look at the rendered page before writing the CSS, not after.
