## Decisions

1. **This list replaces MIP-0056.tasks rows 1–8 for the store.** MIP-0056 wrote raw files and
   Parquet into git on marola-oods's `main`; this MIP keeps its adapters, planner, columns and
   fixtures and writes the lake instead (§5.1). Row 14's tests are MIP-0056.tasks row 2's.
   MIP-0056's PDF channel (its row 7) stays a later row of its own.
2. **The site's read path is not here.** `site.yml`'s download of `exports/` with the read-only token
   (§5.5) is marola-site's own task, filed there once row 11's exports exist.
3. **Facility and trail snapshot readers** (so a build makes no Overpass call at all) are a
   follow-up in marola-app after row 10, not part of creating the tables.
4. **Rows 1–11 and 22 are tracked in marola-oods** (the maintainer, 2026-10-06), whichever repo the PR
   lands in, under the parent marola-dev/marola#672; a marola-app PR closes its row with
   `Closes marola-dev/marola-oods#N`.
5. **Schema first** (the maintainer, 2026-10-05; revised 2026-10-06 on marola-dev/marola-oods#22): the tables are numbered migrations in marola-oods's `lake/`, next to the views and checks, released by tag as `marola-oods-lake-<tag>.tar.gz`. marola-app pins the tag (row 4) and `DuckLakeStore` applies only what is pending, on attach inside an `oods-lake` job (row 5), so the bucket's catalog is created by the first `beach-etl.yml` run and never written from a laptop. The schema has one home, the SQL; a later change is a new `NNNN_*.sql`, never a rebuilt lake. The Scala row types are checked against it (row 4), not generated from it: `kyo-schema` 1.0.0-RC7 has no DDL generator and `kyo-sql` no DuckDB backend. Row 22 is listed last to keep the filed issue numbers; it runs first.
6. **Optional later**: a backfill that re-dispatches itself with `GITHUB_TOKEN`, capped in hops.
