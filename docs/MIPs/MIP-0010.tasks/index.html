    MIP-0010 tasks¶

    Ordered delivery of MIP-0010 as stacked PRs (.claude/skills/mip-tasks/SKILL.md, scripts/stack.sh). Branch mip-0010/<k>-<slug>; merge bottom-up within a lane, scripts/stack.sh restack after each squash-merge.

    Scope is v1 only: the local mlflow server path (MIP Phase 0). The hosted tracking-server path (MIP §4.5, Phase 2) is out of scope for every task below: it needs Phase 1 (the Telegram bot, MIP-0002) done first per AGENTS.md's phase-discipline rule, and the human go-ahead the cost rule requires before any paid cloud resource, so there is nothing to build here yet regardless.

    Revised while building task 6 (2026-09-05): the tracing lane is now stacked on the ledger lane: task 5 branches from task 4, task 6 from task 5, because MlflowTracing needs two things the ledger lane owns: MAROLA_MLFLOW_TRACKING_URI/MAROLA_MLFLOW_EXPERIMENT in AppConfig (task 3) and the experiment name → id lookup (MlflowApi, extracted from task 2's ledger), since MLflow's OTLP endpoint takes an experiment id header. Task 7 (pure Python, no code dependency) is stacked on task 6 as well, purely so the stack tooling's numbered-chain convention holds (scripts/stack.sh/uprds.sh derive task k's base as task k-1); merge order is 1 → 2 → 3 → 4 → 5 → 6 → 7. The paragraph below is kept as the original plan.

    Three independent lanes, not one chain: the table's numbering is delivery order within a lane, not a single dependency chain across all seven. Real code dependency:

    • Ledger lane (1 → 2 → 3 → 4): each based on the previous, per scripts/stack.sh's normal numbered-branch convention.
    • Tracing lane (5 → 6): touches Telemetry/AppConfig/cli/Main, never RunLedger; task 5 branches from main directly (not from task 4), task 6 from task 5.
    • DSPy lane (7): pure Python, zero Scala dependency; branches from main directly.

    The three lanes can be built in parallel (three fresh sessions/agents at once, per the skill's "one task, one session" step). Expect one small, mechanical conflict where lanes overlap in AppConfig.scala (ledger adds MAROLA_MLFLOW_TRACKING_URI/MAROLA_MLFLOW_EXPERIMENT, tracing adds MAROLA_TRACES); whichever lane merges second resolves it on restack, not a redesign.

    1. Local server only, via compose, not nixpkgs (OQ2): ghcr.io/mlflow/mlflow in a docker-compose.yml profile, never added to flake.nix's default shell or the runtime Dockerfile (MIP §8: "a heavy Python dependency"). Task 3 pins the exact tag it first uses.

    3. Experiment naming (OQ6): marola/<kind> as already used throughout MIP §5: marola/benchmark, marola/prompt-compile, marola/finetune (later, unbuilt), marola/traces.
    4. Hosted tracking-server auth (OQ1) and self-hosting MLflow (MIP §4.5) are not tasks here — Phase 2, blocked on Phase 1 and the cost-confirmation gate regardless of MIP status.
